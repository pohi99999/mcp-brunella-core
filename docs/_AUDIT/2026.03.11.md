# Brunella rendszeraudit — 2026.03.11

## Rövid vezetői összefoglaló

A jelenlegi kép alapján a `mcp-brunella-core` egy **nagyon ambiciózus, funkcionálisan gazdag, valódi problémákra épített AI operációs rendszer-jellegű platform**, amelynek legerősebb része a széles integrációs felület, a többügynökös gondolkodás és a gyors iterációs képesség. A rendszer nem proof-of-concept szinten áll: több alrendszere már most is ténylegesen használható.

Ugyanakkor a projekt legnagyobb kihívása már nem a feature-hiány, hanem a **komplexitás kontrollálása**. A kódbázisban egyszerre van jelen:

- Node.js backend
- Python alrendszer
- React dashboard
- MCP szerverek és kliensek
- Cloudflare edge worker réteg
- sok dokumentációs és workflow-réteg
- több, részben átfedő integrációs útvonal

Ez óriási potenciál, de egyben karbantarthatósági kockázat is.

## Aktuális állapotkép

### Ami kifejezetten erős

- **Valós multi-agent architektúra**: a rendszer nem egyetlen chatfelületből áll, hanem ténylegesen külön szerepkörű agentekre épül.
- **Hybrid execution modell**: local + cloud + edge együttműködés.
- **Dashboard + CLI + API + MCP** négyrétegű elérés.
- **Cloudflare/D1/edge irány** jó stratégiai döntés, mert skálázható és modern.
- **Dokumentáltság mennyisége** kiemelkedő; ritka, hogy egy ilyen projekthez ennyi belső kontextus tartozzon.
- **Gyors javíthatóság**: a mai sessionben több gyökérokot is gyorsan lehetett izolálni és javítani.

### Ami most a fő kockázat

- **Konfigurációs drift**: több worker URL, több környezet, részben elavult dokumentációk.
- **Túl sok útvonal ugyanarra a feladatra**: CLI, MCP, HTTP, Socket, Edge proxy — néhol átfednek.
- **Dokumentációs széttartás**: sok fájl pontos, de nem mindig ugyanaz az igazságforrás.
- **Technikai adósság a peremeken**: néhány parancs működik, de kerülőúton vagy örökölt logikán keresztül.
- **Operációs komplexitás**: a rendszer működtetése már külön kompetencia.

## Mai audit fő megállapításai

### 1. D1 / Cloudflare Access

A D1 adatbázis **rendben működik**, a probléma nem magában az adatbázisban volt, hanem a hibás worker-címzésben.

A helyes felosztás jelenleg:

- **CEAN orchestrator / D1 proxy**: `cean-orchestrator.iam-dd1.workers.dev`
- **chat sync worker**: `bas-orchestrator.peterpohankapersonal.workers.dev`
- **Access mögé tett, ezért félrevezető worker**: `bas-orchestrator.iam-dd1.workers.dev`

Következtetés: a fallback oka URL-szintű routing hiba volt, nem D1 oldali adatvesztés vagy schema-hiba.

### 2. CLI audit

A `tests` parancsoknál valódi használhatósági hibák voltak:

- `tests status` hibás tool-útvonalon ment
- `tests results` rossz JSON választ feltételezett
- a CLI feleslegesen MCP-n keresztül próbált lokális státuszt lekérni

Ezeket HTTP-alapú útra tereltem, ami sokkal stabilabb és dashboard-kompatibilisabb.

### 3. Edge / worker topológia

A projektben korábban több worker-szerep részben összemosódott:

- orchestration worker
- D1 proxy worker
- chat worker
- edge task worker

A mai javítások után ez tisztább, de hosszú távon még mindig érdemes **névkonvenció és responsibility boundary** szinten tovább szigorítani.

## Átfogó értékelés

### Architektúra: 8.5/10

Erős, modern, skálázható alapok. A hybrid local/cloud/edge modell stratégiailag jó. A fő gond nem a tervezés minősége, hanem a rendszer természetes kinövése.

### Kódminőség: 7.5/10

Sok helyen jó a struktúra és a szeparáció, de a régebbi és újabb rétegek között látszik a növekedés nyoma. Vannak erős részek és vannak örökölt sarkok.

### Üzemeltethetőség: 6.5/10

Működik, de még túl sok implicit tudást igényel. Egy új fejlesztő vagy operátor számára nem minden útvonal evidens.

### Termékesíthetőség: 8/10

Nagyon jó alap egy komoly, agent-alapú termékhez. A következő szinthez azonban stabilizálni kell a platformréteget, különben a feature-bőség elviszi a fókuszt.

### Dokumentáltság: 8/10

Rengeteg anyag van, ami erősség. A következő lépés már nem a mennyiség növelése, hanem a **kanonikus dokumentáció kijelölése**.

## Mit javasolnék optimalizálásra

## 1. Prioritás — konfiguráció konszolidáció

Hozzatok létre egyetlen, kanonikus konfigurációs mátrixot, ami pontosan megmondja:

- melyik env változó mire való
- melyik worker melyik felelősséghez tartozik
- melyik URL publikus
- melyik Access mögötti
- melyik fallback és melyik first-class production path

Javaslat:

- `docs/_AUDIT/ENVIRONMENT_MATRIX.md`
- `docs/_AUDIT/WORKER_TOPOLOGY.md`

## 2. Prioritás — route inventory automatizálás

A rendszerben sok API route van. Érdemes generálni egy automatikus route inventory-t, pl. build idején vagy dev audit scriptből:

- Express route-ok
- CLI parancsok
- dashboard API hívások
- Cloudflare worker endpointok

Cél: azonnal látszódjon, ha valami nincs bekötve vagy elavult.

## 3. Prioritás — CLI egyszerűsítés

A CLI-ben azt a szabályt javaslom, hogy:

- **lokális státusz / dashboard-jellegű funkció → HTTP API**
- **agent delegation / tool orchestration → MCP**
- **hosszú folyamat / cloud delegáció → edge / async flow**

Ez csökkenti a rejtett hibákat és a “miért indult el közben egy másik alrendszer?” típusú meglepetéseket.

## 4. Prioritás — dokumentációs igazságforrások kijelölése

Javasolt elsődleges források:

- `README.md` → termék és indulás
- `conductor/tracks.md` → aktív munka
- `docs/PROJECT_ARCHITECTURE_DIAGRAM.md` vagy ennek utódja → rendszerkép
- egy dedikált env/worker mátrix → deploy truth

Minden más legyen másodlagos vagy archív.

## 5. Prioritás — audit/health parancsok standardizálása

Nagyon hasznos lenne egy stabil, egyparancsos ellenőrző réteg, például:

- `brunella doctor`
- `brunella audit routes`
- `brunella audit edge`
- `brunella audit config`

Ezek ne általános célú debug eszközök legyenek, hanem fix, determinisztikus auditok.

## 6. Prioritás — edge boundary tisztítás

A Cloudflare rétegben javasolt explicit szeparáció:

- **orchestrator**
- **chat sync**
- **AI proxy**
- **browser / automation**
- **D1/KV utility endpoints**

Minél kevesebb “egy worker több szerepet is részben visz” jellegű átfedés marad, annál jobb lesz az operációs tisztaság.

## Fejlesztési szempontú ajánlások

### Rövid táv (1–2 hét)

- env és worker topológia dokumentálása
- CLI audit parancsok stabilizálása
- Cloudflare route inventory tisztítása
- dashboard API usage végigellenőrzése

### Középtáv (2–6 hét)

- route inventory generátor
- config validator bővítése worker-role ellenőrzéssel
- MCP dependency hibák izolálása / optionalizálása
- kritikus parancsokhoz smoke test suite

### Hosszú táv (1–3 hónap)

- platform core vs experimental modules szétválasztása
- plugin-szerű agent capability registry
- operátori dokumentáció külön rétegben
- release engineering / environment promotion modell (dev → staging → prod)

## Mit tartok a projekt legnagyobb értékének

A Brunella nem csak technikai szempontból érdekes. A projekt legnagyobb értéke, hogy **egy teljes AI-partner ökoszisztéma irányába megy**, nem csak egy LLM wrapper felé. Ez ritka és stratégiailag sokkal erősebb.

A projekt már most is azt mutatja, hogy:

- lehet valódi munkafolyamatokat AI-val összehangolni,
- lehet agenteket specializálni,
- lehet dashboardot, CLI-t és API-t egy rendszerbe fogni,
- és lehet olyan platformot építeni, ami túlmutat a sima chat UX-en.

## Záró értékelés

Ha ezt sikerül jól megfogni, akkor a Brunella nemcsak technikai demonstráció marad, hanem egy stabil, bővíthető, termékesíthető AI platformmá válhat.
